A web artifact is not your live website

For a live site with acceptable layout but weak type or color, start with the existing site. Capture two or three representative screens, ask for a bounded review of type, color, spacing, and contrast, then inspect a small token change before touching components. This is a proposed low-cost first step, not a tested winner.

What the source actually requires

Web Artifacts Builder specifies React 18, TypeScript, Vite, Parcel, Tailwind CSS, and shadcn/ui. It runs repository scripts to initialize and bundle an artifact. The resulting bundle.html is meant for a Claude conversation. Its file calls testing optional. These are author instructions, not proof that the scripts run in your environment or that the UI works.

A GitHub user asked how this differs from Frontend Design. A separate Claude Code user with a live site asked which design option to use when the layout was fine but color and typography needed work. Those are individual questions, not evidence that one workflow produces better results.

Decision

Do not add Web Artifacts Builder to the general website-redesign shortlist. Its narrow packaging job is useful only when the requested deliverable is a complex, single-file Claude artifact. Keep a live-site correction in the real repository and verify its rendered result.

Not tested: We did not install either skill, run the scripts, inspect a generated artifact, or compare a token-only edit with a skill-assisted edit. Both main-source files can change.
